io_scheduler Execution Slides

How io_scheduler.py's Scheduler.run() drives tcp_server and echo_handler together with select() and the Task wrapper — from one connection coming in, through a client sending a message and getting a reply, covering one full request/response cycle, laid out as a static page. (Same approach as the yieldo execution slides.)

Why Task exists
The ready queue needs to hold plain callback functions as well as coroutines, so the scheduler can drive both uniformly with func() without caring which is which.
But a coroutine object can't be called like a normal function. Calling coro() raises TypeError: 'coroutine' object is not callable — it has to be driven with coro.send(None) instead.
To hide that difference from the scheduler, Task is a wrapper object that makes a coroutine look like an ordinary callable function.

Things worth noting while building this page

1

self.current is not in __init__

Scheduler.__init__ only initializes ready·sleeping·_read_waiting·_write_waiting — it never declares current. Python doesn't require attributes to be pre-declared, so this attribute only comes into existence in STEP 3, the first time Task.__call__ runs sched.current = self. Reading self.current before that would have raised AttributeError, but sleep/recv/send/accept are only ever called from inside an already-running Task, so that path never actually happens.

2

Unlike yieldo.py, everything gets drained in one go

yieldo.py's run() dispatched only one item per outer-loop turn, but this scheduler drains things in bulk in three separate places — a single select() call moves every ready fd over with for fd in can_read/can_write, every expired timer gets pulled out with while self.sleeping: ... else: break, and then while self.ready: runs through everything piled up in ready. That's also why the newly created echo_handler in STEP 8 runs right away inside that same while self.ready: loop instead of waiting for the next outer iteration — although in this particular example, echo_handler actually ends up running in STEP 9, not STEP 8, because tcp_server is still inside while self.ready: and echo_handler has only just been added to ready (it gets popped on the next iteration).

3

sched.current and self.current are the same thing

Task.__call__ lives outside the class, so it writes to the global sched directly as sched.current = self. The Scheduler's own methods (sleep/recv/send/accept), on the other hand, write self.current. It's easy to get confused, but sched = Scheduler() is the only instance and these methods always run with self is sched, so both spellings point at exactly the same attribute.

4

Registration (read_wait) and consumption (select's pop) are a matched pair

All three of accept/recv/send follow the exact same pattern — "put the current Task into _read_waiting or _write_waiting, clear current, and hand control back." That symmetry is why the listening socket → tcp_server entry registered in STEP 4 comes back out exactly via self._read_waiting.pop(fd) in STEP 6 — _read_waiting is just a plain dict keyed by fd, with no ordering guarantee of its own.

5

The request/response cycle closes exactly one loop

The state where echo_handler registered itself in _read_waiting via recv() in STEP 9 is identical to the state after send() finishes and recv() is called again in STEP 16 (listening socket → tcp_server, client socket → echo_handler(client)). The recv → send → recv loop inside while True lands back on exactly the same spot in the state diagram, and STEP 9 through 16 repeat verbatim until the client disconnects.
