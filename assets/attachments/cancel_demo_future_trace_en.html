cancel_demo_future Execution Slides

How cancel_demo_future.py handles cancellation with Future, from stalled_read waiting on data that will never arrive to it getting cancelled by timeout_after. This demo only ever reads a socket, so current and _write_waiting are left out, and the extra room instead goes toward showing the relationship and state between Task and Future. (Same approach as the yieldo/io_scheduler execution slides)

Things worth noting while building this page

1

The ready queue doesn't distinguish a Task from a plain function

As shown in STEP 4·5·6·7·8, whatever gets pulled in via heapq.heappop(self.sleeping)[2]() or sched.call_soon(lambda ...) is not a Task — it's just a plain lambda. sched.run()'s while self.ready: func = self.ready.popleft(); func() doesn't care what it is, it just calls func() — which is exactly why this page draws Tasks as cards and plain callbacks as pill-shaped chips, so the two stay visually distinct.

2

_fut_waiter is the sole link cancellation relies on

Task.cancel() is just two lines: if self._fut_waiter is not None: return self._fut_waiter.cancel(). It doesn't need to know what this Task is currently waiting on — a socket read, a sleep, anything else — it just cancels that one Future, and _run_callbacks() takes care of the rest. That's the core payoff of introducing Future, in contrast to cancel_demo.py's waiting_kind/waiting_key approach.

3

Callbacks run in registration order, and always one turn late

Future._run_callbacks() doesn't call callbacks immediately — it only ever schedules them onto ready via sched.call_soon(lambda cb=cb: cb(self)). In STEP 6, a single call to _fut_waiter.cancel() schedules two callbacks at once (cleanup and _wakeup), but they actually run split across STEP 7 and 8, on the next spins of while self.ready.

4

_wakeup branches between a result and a cancellation in the same function

Task._wakeup(future) uses a single check, future.cancelled(), to decide between a normal resume (self()) and a cancelled resume (self(exc=CancelledError())). In STEP 6, timeout_after had cancelled() == False and was resumed the ordinary way via coro.send(None); in STEP 8, stalled_read had cancelled() == True and was resumed via coro.throw(exc) instead — both paths are handled by the exact same _wakeup code.
