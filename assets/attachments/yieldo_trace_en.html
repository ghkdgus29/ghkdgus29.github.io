Things worth noting while building this page

1

The sleeping heap stores an absolute deadline, not "time remaining"

The original slides wrote entries like (4sec, 1, countdown(5)) as "seconds remaining", but the actual code (sleep(), L27) stores an absolute timestamp computed as time.time() + delay. So this page keeps the raw deadline value on each chip and shows the current t (clock) separately in the top-right of each slide instead — "time remaining" is something the reader computes as deadline − t. In STEP 6, countdown's deadline stays at 4 while t moves from 0→1 — that's exactly where this distinction shows up.

2

Even when ready is empty, only one expired timer wakes up at a time

L38-43 pulls out exactly one item with heapq.heappop and pushes it onto ready. That's why in STEP 5→6, even though sleeping held two entries, only countup — the one with the earlier deadline — got popped. Later, when both coroutines' deadlines land on the same value (t=4), they get handled across two separate iterations for the same reason: on the second pop, the clock has already reached that deadline, so delta ≤ 0, and thanks to the if delta > 0 guard on L41, the unnecessary time.sleep(0) is skipped. (io_scheduler.py's run() differs here — its while self.sleeping: ... drains every expired entry in one go.)

3

When deadlines tie, sequence decides the order

This is where the heap's 3-tuple (deadline, sequence, coro) earns its keep. Coroutine objects can't be compared with <, so when deadlines match, whichever one called sleep() first — and thus got the smaller sequence — always wakes first. That's why, at every point where the two coroutines' deadlines coincide, "Down N" is always printed before "Up N".

4

L49's if self.current: never actually fires in this example

Because sleep() always "erases" self.current by setting it to None before await switch() (L30), this condition is always false once send(None) returns. This branch exists to cover a coroutine that calls await switch() directly, without going through sched.sleep(), just to "yield its turn" — the countdown/countup example never takes that path, so the branch reads like dead code. Noting that it's there as a defensive guard for the scheduler's general design should keep readers from getting confused by it.
