io_scheduler 실행 슬라이드

io_scheduler.py의 Scheduler.run()이 tcp_server와 echo_handler를 select()· Task 래퍼와 함께 어떻게 굴리는지, 접속 한 건이 들어와 클라이언트가 메시지를 보내고 응답을 받기까지 한 번의 요청-응답 사이클 전체를 정적 페이지로 정리한 것입니다. (yieldo 실행 슬라이드와 같은 방식)

ready — 실행 대기 중인 Task sleeping — 이 예제에선 쓰이지 않는 타이머 힙 current — 지금 send(None)으로 구동 중 _read_waiting / _write_waiting — fd → 콜백(Task) dict console — print() 출력
1. 초기 상태 2. new_task(tcp_server) 3. dispatch → tcp_server 4. accept() 등록 5. select 블로킹 6. 접속 → requeue 7. accept() 반환·print 8. echo_handler 생성 9. echo_handler recv() 등록 10. select 블로킹 (read) 11. 메시지 도착 → requeue 12. recv() 반환 13. send() 등록 14. select 블로킹 (write) 15. writable → requeue 16. send() 반환·recv() 재등록

Task를 쓰는 이유
ready 큐엔 coroutine만이 아니라 일반 콜백 함수도 올 수 있어야 스케줄러가 둘을 구분하지 않고 func()처럼 균일하게 돌릴 수 있다.
하지만 coroutine 객체는 일반 함수처럼 직접 호출할 수 없다. coro()는 TypeError: 'coroutine' object is not callable에러를 발생시키므로, coro.send(None)으로 호출해야 한다.
이러한 차이를 스케줄러 입장에서는 모르게 하기 위해, Task는 코루틴을 감싸 호출 가능한 일반함수처럼 보이게 만드는 래퍼 객체이다.

슬라이드를 옮기며 짚어둘 것들

1

self.current는 __init__에 없다

Scheduler.__init__은 ready·sleeping·_read_waiting·_write_waiting만 초기화하고 current는 선언하지 않습니다. Python은 속성을 미리 선언할 필요가 없으니, STEP 3에서 Task.__call__이 처음으로 sched.current = self를 실행할 때 비로소 이 속성이 생깁니다. 그 전까지 self.current를 읽으면 AttributeError가 났을 텐데, sleep/recv/send/accept는 전부 이미 실행 중인 Task 안에서만 호출되므로 실제로 그 경로는 발생하지 않습니다.

2

yieldo.py와 달리, 한 번에 다 처리한다

yieldo.py의 run()은 바깥 루프 한 바퀴에 하나만 디스패치했지만, 이 스케줄러는 세 군데서 전부 "몰아서" 처리합니다 — select() 한 번의 결과로 준비된 fd를 for fd in can_read/ can_write로 전부 옮기고, 만료된 타이머는 while self.sleeping: ... else: break로 전부 꺼낸 다음, while self.ready:로 ready에 쌓인 걸 전부 다 돌립니다. STEP 8에서 새로 만든 echo_handler가 같은 while self.ready: 안에서 곧바로(다음 바깥 루프까지 기다리지 않고) 실행되는 것도 이 때문입니다 — 다만 이번 예제에선 echo_handler가 STEP 8이 아니라 STEP 9에서 실행되는데, 그 이유는 tcp_server가 아직 while self.ready: 안에 남아 있고 ready에 이제 막 echo_handler 하나만 들어왔기 때문입니다(다음 반복에서 popleft됨).

3

sched.current와 self.current는 같은 것

Task.__call__은 클래스 밖에 있어서 sched.current = self처럼 전역 sched를 직접 씁니다. 반면 Scheduler 자신의 메서드(sleep/recv/send/accept)는 self.current로 씁니다. 헷갈리기 쉽지만 sched = Scheduler() 하나뿐인 싱글턴이고 이 메서드들은 항상 self is sched인 채로 호출되므로, 두 표기는 완전히 같은 속성을 가리킵니다.

4

등록(read_wait)과 소비(select의 pop)가 짝을 이룬다

accept/recv/send 세 메서드 모두 "지금 Task를 _read_waiting 또는 _write_waiting에 넣고 current를 비운 뒤 제어권을 넘긴다"는 동일한 패턴을 씁니다. STEP 4에서 등록된 listening socket → tcp_server가 STEP 6에서 self._read_waiting.pop(fd)로 정확히 다시 튀어나오는 것도 이 대칭 때문입니다 — _read_waiting은 fd를 키로 하는 평범한 dict일 뿐, 별도의 순서 보장은 없습니다.

5

요청-응답 사이클이 정확히 한 바퀴 돈다

STEP 9에서 echo_handler가 recv()로 _read_waiting에 등록된 상태와, STEP 16에서 send()가 끝나고 다시 recv()를 호출해 등록된 상태는 완전히 동일합니다 (listening socket → tcp_server, client socket → echo_handler(client)). recv → send → recv로 이어지는 while True 루프가 상태 다이어그램 위에서도 정확히 제자리로 돌아온다는 뜻이고, 클라이언트가 연결을 끊기 전까지는 STEP 9~16이 그대로 반복됩니다.
